Gitのブランチの運用、コミットの単位とメッセージ、プルリクエストの作り方、マージの方法を決めます。ブランチの運用は[GitHub Flow](https://docs.github.com/ja/get-started/using-github/github-flow)、コミットメッセージは[Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/)に従います。

プルリクエストをレビューするときの進め方は[レビューのチェックリスト](/coding-guidelines/quality/review-checklist/)、秘密情報の扱いは[セキュリティ](/coding-guidelines/quality/security/)のページで扱います。

## mainブランチから作業ブランチを切って作業する

作業は、`main` ブランチから切った作業ブランチで行い、プルリクエストを通して `main` にマージします。`main` は常に公開できる状態に保ちます。

準拠レベル：**必須**

**理由**

`main` が常に公開できる状態なら、いつでも公開でき、急ぎの修正もすぐに出せます。作業ブランチを1つの目的ごとに分けておけば、作業途中の変更が、ほかの変更の公開を止めることもありません。

`develop` などの長く使い続けるブランチは作りません。ブランチが増えるほど、どのブランチに何が入っているかを把握するのが難しくなるためです。

**良い例**

```sh
git switch main
git pull
git switch -c feat/order-history-filter
```

**悪い例**

```sh
# mainで直接作業する
git switch main
git commit -am "絞り込みを追加"
```

## mainへの直接のプッシュをGitHubの設定で禁止する

`main` ブランチには、GitHubのブランチの保護（ルールセット）を設定し、プルリクエストを通さない変更と、CIが通っていない変更をマージできないようにします。

準拠レベル：**必須**

**理由**

「直接プッシュしない」と決めるだけでは、うっかりや急ぎのときに破られます。GitHubの設定で禁止すれば、すべての変更が必ずCIとレビューを通ります。AIに作業させる場合も、誤って `main` を書き換えられることがありません。

**良い例**

```md
<!-- GitHubのルールセット（mainブランチ） -->
- Require a pull request before merging：有効
- Require status checks to pass：有効（フォーマット、Lint、テストのジョブを指定）
- Block force pushes：有効
```

**悪い例**

```md
<!-- mainブランチに保護の設定がない -->
README.mdに「mainに直接プッシュしないこと」とだけ書いている
```

## ブランチ名は「種類/内容」の形にする

作業ブランチの名前は、コミットメッセージと同じ種類（`feat`、`fix` など）に、作業の内容を表す英語のケバブケースを `/` でつなげます。Issueがある場合は、内容の前に番号を付けてもかまいません。

準拠レベル：**推奨**

**理由**

ブランチの一覧を見るだけで、それぞれが何の作業かが分かります。種類が先頭にそろっていれば、ブランチを種類ごとに並べたり、絞り込んだりすることもできます。

**良い例**

```text
feat/order-history-filter
fix/cart-total-rounding
docs/readme-setup
fix/128-payment-retry
```

**悪い例**

```text
yamada-work
fix
new_feature_2
注文履歴
```

## コミットメッセージはConventional Commitsの形式で、要約は日本語で書く

コミットメッセージの1行目は `種類: 要約` の形にします。種類は次の表から選び、要約は日本語で書きます。

| 種類 | 使う場面 |
| :-- | :-- |
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | ドキュメントだけの変更 |
| `style` | 書式だけの変更（動きは変わらない） |
| `refactor` | 機能を変えないコードの整理 |
| `perf` | 性能の改善 |
| `test` | テストの追加・修正 |
| `build` | ビルドの設定や依存パッケージの変更 |
| `ci` | CIの設定の変更 |
| `chore` | 上記に当てはまらない雑務 |
| `revert` | 以前のコミットの取り消し |

互換性のない変更には、種類の後ろに `!` を付けます（`feat!:`）。

準拠レベル：**必須**

**理由**

形式がそろっていれば、履歴を見て、どのコミットが機能の追加で、どれが不具合の修正なのかがすぐに分かります。種類を選ぶときに「このコミットは何の変更か」を考えることになり、1つのコミットに複数の種類の変更を混ぜることも防げます。

要約を日本語にするのは、コメントやプルリクエストと言語をそろえ、細かい内容まで誤解なく伝えるためです。

**良い例**

```text
feat: 注文履歴に期間の絞り込みを追加
fix: 送料無料の判定で基準額ちょうどを対象外にしていた不具合を修正
refactor: 送料の計算をコンポーネントから関数に切り出す
feat!: 商品APIのレスポンスを新しい形式に変更
```

**悪い例**

```text
修正
update
feat: いろいろ対応
fix: レビュー指摘対応
```

## 要約は1行で何をしたかを書き、理由は本文に書く

コミットメッセージの1行目には、何をしたかを1行で書きます。なぜその変更が必要だったのかや、ほかの方法を選ばなかった理由は、1行空けて本文に書きます。

準拠レベル：**推奨**

**理由**

1行目は、履歴の一覧やGitHubの画面で表示される部分なので、短く、何をしたかが分かるようにします。一方で、「なぜ」はコードにも差分にも残らないため、本文に書いておかないと、後から変更の意図を知る手段がなくなります。

**良い例**

```text
fix: 送料無料の判定で基準額ちょうどを対象外にしていた不具合を修正

基準額「以上」を無料とする仕様に対し、「より大きい」で判定していた。
小計がちょうど5,000円の注文で送料がかかっていた。
```

**悪い例**

```text
fix: subtotal > FREE_SHIPPING_THRESHOLD を subtotal >= FREE_SHIPPING_THRESHOLD に変更して、5,000円ちょうどのときも送料を無料にするようにした（問い合わせがあったため）
```

## 1つのコミットには1つの変更だけを入れる

1つのコミットには、1つの目的の変更だけを入れます。機能の追加とリファクタリング、書式の修正などを1つのコミットに混ぜません。

準拠レベル：**推奨**

**理由**

目的の異なる変更が混ざっていると、レビューで何が意図した変更なのかを読み分けるのが難しくなります。後から1つの変更だけを取り消したいときにも、`git revert` で切り離せません。

**良い例**

```text
refactor: 送料の計算をコンポーネントから関数に切り出す
feat: 離島への配送に追加の送料をかける
```

**悪い例**

```text
feat: 離島の送料を追加、送料の計算を整理、ついでにインデントを修正
```

## ビルドの生成物や依存パッケージをコミットしない

`node_modules`、ビルドの出力（`dist` など）、テストの結果、エディタやOSが作るファイルは、`.gitignore` に書いてコミットしません。依存パッケージのバージョンを固定するlockfile（`package-lock.json`）はコミットします。

準拠レベル：**必須**

**理由**

生成物はソースコードから作り直せるため、コミットしても差分が大きくなるだけです。手で編集されて、ソースコードと食い違う原因にもなります。lockfileは生成物ではなく、どのバージョンの依存パッケージを使うかの記録なので、コミットします（理由は[セキュリティ](/coding-guidelines/quality/security/)を参照）。

**良い例**

```text title=".gitignore"
node_modules/
dist/
coverage/
test-results/
playwright-report/
.DS_Store
```

**悪い例**

```text title=".gitignore"
node_modules/
# lockfileを無視している
package-lock.json
```

## プルリクエストは1つの目的に絞り、小さく保つ

プルリクエストは、1つの目的の変更だけにします。差分が大きくなりそうなときは、リファクタリングと機能の追加を分けるなど、順にマージできる単位に分けます。

準拠レベル：**推奨**

**理由**

差分が大きいほど、レビューする人は全体を把握できなくなり、問題を見落とします。小さなプルリクエストなら、レビューが早く終わり、問題があったときに取り消すのも簡単です。

目安として、自動生成されたファイルを除いて、変更が400行を超えるなら分けられないかを考えます。

**良い例**

```text
#41 refactor: 送料の計算をコンポーネントから関数に切り出す
#42 feat: 離島への配送に追加の送料をかける（#41 のマージ後に作成）
```

**悪い例**

```text
#41 feat: 配送まわりの改修（送料の計算の整理、離島の送料の追加、配送日の指定、デザインの調整）
```

## プルリクエストの説明に目的、変更内容、確認したことを書く

プルリクエストの説明には、次の内容を書きます。リポジトリにはテンプレート（`.github/pull_request_template.md`）を置きます。

- 目的：なぜこの変更が必要か。Issueがあれば番号を書く
- 変更内容：何を変えたか
- 確認したこと：どの環境で、何を確かめたか
- レビューしてほしい点：特に見てほしい箇所や、迷った点

準拠レベル：**推奨**

**理由**

レビューする人は、目的が分からないと、変更が妥当かを判断できません。確認したことが書いてあれば、レビューする人は、確認が足りない部分に絞って見られます。説明はマージ後も残るため、後から変更の経緯を調べるときの手がかりにもなります。

確かめる方法は[検証](/coding-guidelines/quality/verification/)を参照してください。

**良い例**

```md title=".github/pull_request_template.md"
## 目的

<!-- なぜこの変更が必要か。Issueがあれば「Closes #123」と書く -->

## 変更内容

## 確認したこと

<!-- 確認した環境と内容 -->

## レビューしてほしい点
```

**悪い例**

```md
注文履歴の修正です。よろしくお願いします。
```

## CIが通り、レビューで承認されてからマージする

プルリクエストは、CIのすべてのジョブが成功し、レビューで承認されてからマージします。1人で開発している場合も、プルリクエストを作り、[レビューのチェックリスト](/coding-guidelines/quality/review-checklist/)に沿って自分でレビューしてからマージします。

準拠レベル：**必須**

**理由**

CIとレビューは、問題のある変更が `main` に入るのを防ぐための仕組みです。急いでいるときに飛ばすと、その変更が問題の原因になったときに、公開してから気づくことになります。1人の場合も、プルリクエストの画面で差分を見直すと、エディタで書いているときには気づかなかった問題が見つかります。

**良い例**

```md
<!-- プルリクエストの状態 -->
- ✅ check（フォーマット、Lint）
- ✅ test
- ✅ e2e
- ✅ レビューで承認済み
```

**悪い例**

```md
<!-- プルリクエストの状態 -->
- ❌ e2e（たぶん不安定なだけなので、そのままマージ）
- レビュー待ちだが、急ぎのため管理者の権限でマージ
```

## マージはマージコミットで行う

プルリクエストは、マージコミットを作る方法（GitHubの「Create a merge commit」）でマージします。リポジトリの設定で、スカッシュとリベースによるマージは無効にします。

準拠レベル：**推奨**

**理由**

マージコミットで取り込めば、作業ブランチの1つひとつのコミットが `main` の履歴に残り、変更の経緯を細かくたどれます。どこからどこまでが1つのプルリクエストかも、マージコミットで区切られて分かります。マージの方法を1つに決めておけば、人によって履歴の形がばらつきません。

この方法では作業ブランチのコミットがそのまま残るため、次のルールのとおり、マージする前にコミットを整えます。

**良い例**

```text
*   Merge pull request #42 from example/feat/remote-island-shipping
|\
| * feat: 離島への配送に追加の送料をかける
| * refactor: 送料の計算をコンポーネントから関数に切り出す
|/
*   Merge pull request #41 from example/fix/cart-total-rounding
```

**悪い例**

```text
# プルリクエストごとにマージの方法が異なり、履歴の形がばらつく
* feat: 離島への配送に追加の送料をかける (#42)
*   Merge pull request #41 from example/fix/cart-total-rounding
|\
| * fix: 合計金額の端数の扱いを修正
|/
* refactor: 送料の計算を整理
```

## マージする前に、作業途中のコミットを整える

マージする前に、「WIP」「修正」「レビュー指摘対応」のような作業途中のコミットを、意味のある単位のコミットにまとめます。レビューの指摘への対応は `git commit --fixup` で記録し、マージの前に `git rebase -i --autosquash` でまとめます。

準拠レベル：**推奨**

**理由**

マージコミットで取り込むと、作業ブランチのコミットがすべて `main` に残ります。作業途中のコミットが混ざっていると、履歴から変更の意図が読み取れず、`git bisect` で問題の原因を探すときにも、動かない状態のコミットが邪魔になります。

`--fixup` で記録しておけば、レビューの途中では追加の差分だけを見てもらえ、マージの前に元のコミットへ自動でまとめられます。

**良い例**

```sh
# レビューの指摘を、対象のコミットへの修正として記録する
git commit --fixup a1b2c3d

# マージの前にまとめる
git rebase -i --autosquash main
git push --force-with-lease
```

**悪い例**

```text
* レビュー指摘対応2
* レビュー指摘対応
* WIP
* とりあえず動く
* feat: 離島への配送に追加の送料をかける
```

## 強制プッシュは自分の作業ブランチだけで、--force-with-leaseを付けて行う

履歴を書き換えて強制プッシュするのは、自分だけが使っている作業ブランチに限ります。強制プッシュには `--force` ではなく `--force-with-lease` を使います。`main` には強制プッシュしません。

準拠レベル：**必須**

**理由**

ほかの人も使っているブランチの履歴を書き換えると、その人の手元の履歴と食い違い、作業が失われることがあります。`--force-with-lease` は、自分が最後に取得した後にリモートが更新されていた場合はプッシュを止めるため、ほかの人のコミットを気づかずに消すことを防げます。

**良い例**

```sh
git push --force-with-lease
```

**悪い例**

```sh
git push --force
git push --force origin main
```

## マージした作業ブランチは削除する

マージした作業ブランチは削除します。GitHubの設定で、マージしたブランチを自動で削除するようにします（「Automatically delete head branches」）。

準拠レベル：**推奨**

**理由**

マージ済みのブランチが残っていると、ブランチの一覧から、作業中のブランチを探しにくくなります。マージしたブランチの内容は `main` に入っており、プルリクエストからも復元できるため、残しておく必要はありません。

**良い例**

```sh
# 手元のブランチも、リモートで削除されたものに合わせて整理する
git switch main
git pull --prune
git branch -d feat/order-history-filter
```

**悪い例**

```text
$ git branch -r | wc -l
     148
```
