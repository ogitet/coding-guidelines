---

実装した画面が、対応する環境で正しく表示され、誰でも操作できるかを確かめる方法を決めます。どのブラウザとデバイスに対応するかは[対応ブラウザとデバイス](/coding-guidelines/about/browser-support/)で決めており、このページでは、それをどう確かめるかを扱います。

| 確かめること | 方法 |
| :-- | :-- |
| 表示と操作 | 対応ブラウザと実機での確認 |
| HTMLの正しさ | Nu Html Checker |
| アクセシビリティ | axe、キーボード操作、スクリーンリーダー、拡大表示 |
| 表示の速さ | Lighthouse |

自動テスト（単体、E2E、ビジュアルリグレッション）は[テスト方針](/coding-guidelines/quality/testing/)、守るべきアクセシビリティのルールは[アクセシビリティ](/coding-guidelines/common/accessibility/)のページで扱います。確かめた内容をプルリクエストにどう書くかは[Git](/coding-guidelines/quality/git/)を参照してください。

## 対応するすべてのブラウザで表示と操作を確かめる

画面を追加・変更したら、マージする前に、対応するすべてのブラウザで表示と操作を確かめます。開発に使っているブラウザだけで確かめて終わりにしません。

準拠レベル：**必須**

**理由**

同じコードでも、ブラウザの描画エンジンによって、レイアウトやフォーム部品の見た目、対応しているCSSの機能が異なります。普段使うブラウザで問題がなくても、別のブラウザでは崩れていることがあります。

特にSafariは、iPhoneのほとんどのブラウザが同じ描画エンジンを使うため、確認から外せません。

**良い例**

```md
<!-- プルリクエストの「確認したこと」 -->
- Chrome、Edge、Firefox、Safari（macOS）の最新版で表示と操作を確認
- iPhone（Safari）、Android（Chrome）の実機で表示と操作を確認
```

**悪い例**

```md
<!-- プルリクエストの「確認したこと」 -->
- 手元のChromeで動作確認済み
```

## スマートフォンの表示は実機でも確かめる

スマートフォン向けの表示は、ブラウザの開発者ツールのデバイスモードに加えて、iPhoneとAndroidの実機でも確かめます。

準拠レベル：**推奨**

**理由**

開発者ツールのデバイスモードは、画面の幅を変えているだけで、描画エンジンはパソコンのものです。タッチ操作、ソフトウェアキーボードが開いたときの表示、画面の切り欠き（セーフエリア）、アドレスバーの伸び縮みによる高さの変化などは、実機でしか確かめられません。

手元にない機種での確認が必要な場合は、BrowserStackなどの実機を使えるサービスを使います。

**良い例**

```md
<!-- 確認した内容 -->
- iPhone（Safari）：入力欄にフォーカスしたとき、固定ヘッダーが入力欄に重ならない
- Android（Chrome）：ボタンをタップして、カートに追加される
```

**悪い例**

```md
<!-- 確認した内容 -->
- Chromeのデバイスモード（iPhone 15 Pro）で表示を確認
```

## 空、長い文字列、エラーなどの状態でも表示を確かめる

表示を確かめるときは、見本どおりのデータだけでなく、データが0件、文字列が長い、読み込み中、エラーといった状態でも確かめます。

準拠レベル：**推奨**

**理由**

デザインの見本は、ちょうどよい長さの文字列と、ちょうどよい件数のデータで作られていることがほとんどです。実際のデータでは、長い商品名がはみ出す、0件のときに何も表示されない、通信が遅いと画面が真っ白になる、といった問題が起きます。

通信の遅い状態は、開発者ツールの通信速度の制限（スロットリング）で再現します。

**良い例**

```md
<!-- 確認した状態 -->
- 注文が0件：「注文はまだありません」と表示される
- 商品名が80文字：2行で省略され、レイアウトが崩れない
- 読み込み中：スケルトンが表示される（通信速度を「低速4G」に制限して確認）
- APIがエラー：再読み込みのボタンとエラーの説明が表示される
```

**悪い例**

```md
<!-- 確認した状態 -->
- テスト用のデータ（3件）で表示を確認
```

## 出力されたHTMLをNu Html Checkerで検査する

ページの種類ごとに、ブラウザに出力されたHTMLを[Nu Html Checker](https://validator.w3.org/nu/)で検査し、エラーをなくします。

準拠レベル：**推奨**

**理由**

Markuplintはソースコードを検査しますが、コンポーネントを組み合わせた結果のHTMLまでは検査できません。たとえば、別々のコンポーネントに同じ `id` が書かれている、`p` 要素の中に `div` 要素が入る、といった問題は、出力されたHTMLを検査して初めて見つかります。

静的に出力するサイトは、ビルド結果のファイルを検査します。ブラウザで組み立てる画面は、開発者ツールでコピーしたHTMLを、Nu Html Checkerの画面に貼り付けて検査します。

**良い例**

```json title="package.json（一部）"
{
  "scripts": {
    "validate:html": "java -jar node_modules/vnu-jar/build/dist/vnu.jar --skip-non-html --errors-only dist/"
  }
}
```

**悪い例**

```md
<!-- 確認した内容 -->
- Markuplintが通っているので、HTMLの検査は省略
```

## axeでアクセシビリティを検査する

画面を追加・変更したら、[axe](https://www.deque.com/axe/)で検査し、検出された違反をなくします。主要な画面は、PlaywrightのE2Eテストにaxeの検査を組み込み、CIで自動的に確かめます。

準拠レベル：**必須**

**理由**

コントラスト比の不足、ラベルのない入力欄、名前のないボタンなど、機械的に判定できる問題は、axeで確実に見つけられます。手で確かめるより速く、見落としもありません。

ただし、axeが検出できるのはアクセシビリティの問題の一部です。代替テキストの内容が適切か、操作の順序が自然かといったことは判定できないため、キーボードとスクリーンリーダーでの確認と組み合わせます。

**良い例**

```ts title="e2e/accessibility.spec.ts"
import AxeBuilder from "@axe-core/playwright";
import { expect, test } from "@playwright/test";

test("トップページにアクセシビリティの違反がない", async ({ page }) => {
  await page.goto("/");

  const results = await new AxeBuilder({ page })
    .withTags(["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"])
    .analyze();

  expect(results.violations).toEqual([]);
});
```

**悪い例**

```ts
// 違反があるルールを除外して、検査を通している
const results = await new AxeBuilder({ page })
  .disableRules(["color-contrast", "label", "button-name"])
  .analyze();
```

## キーボードだけで操作できるかを確かめる

画面を追加・変更したら、マウスを使わず、キーボードだけですべての操作ができるかを確かめます。次の点を見ます。

- `Tab` と `Shift + Tab` で、すべての操作できる要素に、見た目の順どおりにフォーカスが移る
- フォーカスしている位置が、常に見える
- `Enter` や `Space` でボタンやリンクを操作でき、`Esc` でダイアログやメニューを閉じられる
- ダイアログを開いている間は、フォーカスがダイアログの外に出ない。閉じたら、開いたボタンにフォーカスが戻る
- フォーカスが抜け出せなくなる場所がない

準拠レベル：**必須**

**理由**

マウスを使えない人や、スクリーンリーダーを使う人は、キーボードで操作します。キーボードで操作できるかどうかは、axeでは判定できず、実際に操作して確かめるしかありません。

**良い例**

```md
<!-- 確認した内容 -->
- 絞り込みのダイアログ：Tabで開くボタンにフォーカスし、Enterで開く。
  Escで閉じると、フォーカスが開くボタンに戻る
```

**悪い例**

```md
<!-- 確認した内容 -->
- マウスで操作して問題なし
```

## スクリーンリーダーで主要な画面を確かめる

主要な画面と、独自に作った部品（タブ、メニュー、コンボボックスなど）は、スクリーンリーダーで読み上げと操作を確かめます。macOSとiOSではVoiceOver、WindowsではNVDAを使います。

準拠レベル：**推奨**

**理由**

ARIAの使い方の誤りや、読み上げの順序の不自然さ、状態の変化が伝わらないといった問題は、実際に読み上げを聞かないと気づけません。特に、HTMLの標準の要素ではなく独自に作った部品は、役割や状態が正しく伝わっているかを確かめる必要があります。

**良い例**

```md
<!-- 確認した内容 -->
- VoiceOver（macOS + Safari）：タブを切り替えると「選択済み、タブ、2/3」と読み上げられる
- NVDA（Windows + Chrome）：カートに追加すると「カートに追加しました」と読み上げられる
```

**悪い例**

```md
<!-- 確認した内容 -->
- axeで違反がないので、スクリーンリーダーでは確認していない
```

## 拡大と文字サイズの変更で崩れないかを確かめる

ブラウザの文字サイズを200%にした状態と、画面の幅を320pxにした状態（1280pxの画面を400%に拡大した状態に相当）で、内容が欠けたり重なったりしないかを確かめます。

準拠レベル：**推奨**

**理由**

拡大を妨げないためのルールは[アクセシビリティ](/coding-guidelines/common/accessibility/)で決めていますが、ルールを守っていても、高さを固定した要素や、幅を固定したレイアウトがあると、拡大したときに文字が切れたり、横にスクロールしないと読めなくなったりします。こうした崩れは、実際に拡大してみないと気づけません。

**良い例**

```md
<!-- 確認した内容 -->
- ブラウザの文字サイズ「特大」：ボタンの文字が切れない
- 幅320px：横スクロールが出ず、表以外の内容がすべて1列で読める
```

**悪い例**

```md
<!-- 確認した内容 -->
- 幅375px（iPhoneの幅）で表示を確認
```

## 本番用にビルドしたもので最終確認する

マージする前の最終確認と、Lighthouseでの計測は、開発サーバーではなく、本番用にビルドしたものを動かして行います。

準拠レベル：**推奨**

**理由**

開発サーバーは、圧縮されていないコード、変更を即座に反映する仕組み、開発用の警告などを含むため、本番とは動きも速さも異なります。Reactの開発モードで `StrictMode` を有効にしていると、エフェクトが2回実行されるなど、本番では起きない動作もあります。ビルドの設定の誤りによる問題は、ビルドしたものでしか見つかりません。

**良い例**

```sh
npm run build
npm run preview
```

**悪い例**

```sh
# 開発サーバーの画面でLighthouseを計測する
npm run dev
```

## 表示の速さはLighthouseで計測し、Core Web Vitalsの「良好」を目指す

表示の速さは、Lighthouseをモバイルの設定で実行して計測します。目標は、Core Web Vitalsの「良好」の基準です。

| 指標 | 意味 | 良好の基準 |
| :-- | :-- | :-- |
| LCP | 主な内容が表示されるまでの時間 | 2.5秒以下 |
| INP | 操作してから画面が反応するまでの時間 | 200ミリ秒以下 |
| CLS | 読み込み中のレイアウトのずれ | 0.1以下 |

準拠レベル：**推奨**

**理由**

表示が遅い、操作への反応が遅い、読み込み中に表示がずれる、といった問題は、使う人が離れる原因になります。計測せずに「速い」と判断すると、性能の高いパソコンと速い回線で見ているだけ、ということになりがちです。Lighthouseは、モバイルの設定では、遅いCPUと回線を想定して計測します。

拡張機能の影響を受けないように、シークレットウィンドウで計測します。INPは実際の操作が必要なため、ページを読み込むだけのLighthouseの計測では測れません。代わりにTotal Blocking Time（TBT）を目安にし、公開後は実際の利用者のデータで確かめます。

**良い例**

```sh
npm run build
npm run preview
# 別のターミナルで、モバイルの設定（既定）で計測する
npx lighthouse http://localhost:4173/ --view
```

**悪い例**

```sh
# デスクトップの設定だけで計測し、モバイルでの遅さを見落とす
npx lighthouse http://localhost:4173/ --preset=desktop --view
```
