---

ClaudeなどのAIエージェントにコードを書かせるときの、指示の書き方を決めます。すべての作業で守らせることはリポジトリの `AGENTS.md` に書き、作業ごとの依頼では、目的と範囲と完了の条件を伝えます。ページの最後に、ここでのルールをまとめた `AGENTS.md` の雛形を載せています。

## 常に守らせる指示はAGENTS.mdに書く

すべての作業で守らせる指示は、リポジトリのルートに置いた `AGENTS.md` に書きます。ツール専用の指示ファイル（Claude Codeの `CLAUDE.md` など）には、`AGENTS.md` を読み込む指定だけを書きます。

準拠レベル：**推奨**

**理由**

指示をリポジトリに置けば、誰がどの環境でAIを使っても同じ指示が渡り、指示の変更もコードと同じようにレビューできます。`AGENTS.md` は複数のAIエージェントが読む共通のファイル名なので、ツールを替えても指示を書き直さずに済みます。

ツールごとに指示を書き分けると、片方だけを直して内容が食い違います。依頼のたびにプロンプトへ貼り付ける方法も、貼り忘れや版の違いが起きます。

**良い例**

```md title="CLAUDE.md"
@AGENTS.md
```

**悪い例**

```text
.
├── .github/
│   └── copilot-instructions.md   # CLAUDE.md と内容が少しずつ違う
└── CLAUDE.md
```

## この規約はURLで参照させる

`AGENTS.md` では、この規約を [llms-full.txt](/coding-guidelines/llms-full.txt) のURLで参照させます。規約の本文を `AGENTS.md` に書き写しません。

準拠レベル：**必須**

**理由**

書き写すと、規約を改訂したときに `AGENTS.md` の内容が古いまま残ります。URLで参照すれば、常に最新の規約を読ませられます。`llms-full.txt` は、規約の全文をAIが読みやすいテキストにしたものです。読み込む量を抑えたい場合は、補足を省いた `llms-small.txt` を使います。

AIの作業環境からインターネットに接続できない場合に限り、`llms-full.txt` をリポジトリに保存して参照させ、保存した日付を `AGENTS.md` に書きます。

**良い例**

```md title="AGENTS.md（一部）"
## コーディング規約

次の規約に従う。

https://ogitet.github.io/coding-guidelines/llms-full.txt
```

**悪い例**

```md title="AGENTS.md（一部）"
## コーディング規約

- 名前は英語で付ける
- ファイル名はケバブケースにする
- コメントは日本語で書く
（以下、規約の本文を書き写して続く）
```

## プロジェクトで規約と異なる点を書く

プロジェクトの決まりがこの規約と異なる場合は、どのルールがどう異なるかを `AGENTS.md` に書きます。

準拠レベル：**必須**

**理由**

[目的と範囲](/coding-guidelines/about/purpose-and-scope/)にあるとおり、プロジェクトに独自の規約がある場合はそちらを優先します。異なる点が書いていないと、AIはこの規約に従い、プロジェクトの既存のコードと食い違う書き方をします。「既存のコードに合わせる」とだけ書いても、どのルールが対象かをAIは判断できません。

**良い例**

```md title="AGENTS.md（一部）"
### このプロジェクトでの例外

規約の次のルールは、このプロジェクトでは適用しない。

- 「コメントは日本語で書く」：海外のメンバーがいるため、コメントは英語で書く
- 「機能単位でディレクトリをまとめる」：既存の構成に合わせ、`src/components/` と `src/hooks/` に種類ごとに置く
```

**悪い例**

```md title="AGENTS.md（一部）"
### 注意

既存のコードに合わせてください。
```

## 作業に使うコマンドを書く

セットアップ、開発サーバーの起動、ビルド、テスト、フォーマット、Lintのコマンドを、`AGENTS.md` に書きます。

準拠レベル：**必須**

**理由**

コマンドが分かれば、AIは変更のたびに自分でテストとLintを実行し、誤りに気づいて直せます。書いていないと、AIは `package.json` から推測するか、確認を飛ばして作業を終えます。

READMEに同じコマンドを書いている場合は、`AGENTS.md` からREADMEの該当箇所を参照させてもかまいません。

**良い例**

```md title="AGENTS.md（一部）"
## コマンド

| コマンド | 内容 |
| :-- | :-- |
| `npm install` | 依存パッケージを入れる |
| `npm run dev` | 開発サーバーを起動する |
| `npm run build` | 本番用にビルドする |
| `npm test` | テストを実行する |
| `npm run check` | フォーマットとLintを確認する |
```

**悪い例**

```md title="AGENTS.md（一部）"
## コマンド

変更したらテストを実行してください。
```

## コードから読み取れることは書かない

`AGENTS.md` には、コードや設定ファイルを読んでも分からないことだけを書きます。フォーマッタやLintで守らせられるルールも書きません。

準拠レベル：**推奨**

**理由**

`AGENTS.md` は毎回の作業で読み込まれるため、長くなるほど重要な指示が埋もれます。ディレクトリの一覧や使っているライブラリの説明は、コードを読めば分かるうえ、コードを変えると古くなります。書式やLintで判定できるルールは、指示するより、[Lintの設定に入れる](/coding-guidelines/common/format-and-lint/)ほうが確実に守らせられます。

書くのは、移行中のコードの扱い、外部の仕様による制約、過去に決めた方針とその理由など、コードに現れない前提です。

**良い例**

```md title="AGENTS.md（一部）"
## 前提

- `src/legacy/` は移行中の古いコード。2027年3月に削除するため、新しいコードから import しない
- 決済APIはテスト環境でも課金が発生する。テストでは `src/mocks/payment.ts` のモックを使う
```

**悪い例**

```md title="AGENTS.md（一部）"
## 前提

- インデントはスペース2つにする
- `src/components/` にはコンポーネントが入っている
- 読みやすいコードを書く
```

## 指示は言い切り、理由を添える

`AGENTS.md` と依頼の指示は「〜する」「〜しない」と言い切る形で書き、そうする理由を添えます。「なるべく」「適宜」のような、程度をぼかす言葉は使いません。

準拠レベル：**推奨**

**理由**

程度がぼかしてあると、AIはどこまで守ればよいかを判断できず、作業ごとに解釈がぶれます。理由が書いてあれば、指示が直接触れていない場面でも、理由に沿って判断できます。

**良い例**

```md title="AGENTS.md（一部）"
- 日付の処理には `src/utils/date.ts` の関数を使い、`Date` を直接扱わない。タイムゾーンの扱いをこのファイルにまとめているため
```

**悪い例**

```md title="AGENTS.md（一部）"
- 日付の処理は、なるべく `src/utils/date.ts` を使ってください
```

## 事前に確認させる操作と禁止する操作を書く

取り消しにくい操作や、影響が依頼の範囲を超える操作は、`AGENTS.md` に「事前に確認する操作」と「禁止する操作」に分けて書きます。

準拠レベル：**必須**

**理由**

AIは、依頼を達成するために、依存パッケージの追加や設定の変更を自分の判断で進めることがあります。影響の大きい操作を明示しておけば、実行の前に止めて、人が判断できます。何も書かなければ、AIはそれらを止めるべき操作だと判断できません。

「危険な操作はしない」のような書き方では、何が危険かをAIが決めることになるため、操作を具体的に挙げます。

**良い例**

```md title="AGENTS.md（一部）"
## 事前に確認する操作

- 依存パッケージの追加、更新、削除
- フォーマッタ、Lint、TypeScriptの設定の変更
- 依頼された範囲の外にあるファイルの変更

## 禁止する操作

- テストの削除やスキップ、期待値を実装に合わせて書き換えることで、テストを通す
- `git push --force` と、メインブランチへの直接のプッシュ
- `.env` で始まるファイルの読み書き
```

**悪い例**

```md title="AGENTS.md（一部）"
## 注意

危険な操作はしないでください。
```

## 秘密情報を指示に含めない

APIキー、パスワード、個人情報を、`AGENTS.md` や依頼の文面に書きません。`.env` など秘密情報を含むファイルは、AIエージェントが読めないように設定します。

準拠レベル：**必須**

**理由**

依頼の文面や、AIが読み込んだファイルの内容は、AIのサービスに送信されます。`AGENTS.md` はリポジトリにコミットされるため、書いた内容はリポジトリを見られる人すべてに見えます。動作確認に秘密情報が必要な場合は、AIには環境変数の名前だけを伝え、値は人が設定します。

**良い例**

```json title=".claude/settings.json"
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}
```

```text
決済APIのキーは環境変数 PAYMENT_API_KEY から読み込むようにしてください。値は私が .env.local に設定します。
```

**悪い例**

```text
このキーで決済APIの動作確認をしてください：sk_live_xxxxxxxxxxxxxxxx
```

## 1回の依頼は1つの目的に絞る

AIへの依頼は、1回につき1つの目的に絞ります。別の目的の作業は、依頼を分けます。

準拠レベル：**推奨**

**理由**

複数の目的を一度に頼むと、変更が大きくなり、レビューで確かめきれなくなります。目的ごとに分ければ差分が小さくなり、問題があってもその依頼だけをやり直せます。どの変更がどの目的のためのものかも、コミットの単位で分かります。

**良い例**

```text
注文一覧のページ送りを、無限スクロールに変えてください。
```

**悪い例**

```text
注文一覧を無限スクロールにして、ついでに全体をリファクタリングして、テストも増やしておいてください。
```

## 依頼には目的、範囲、完了の条件を書く

AIへの依頼には、何のための変更か（目的）、どこまで変えてよいか（範囲）、何を満たせば終わりか（完了の条件）を書きます。

準拠レベル：**推奨**

**理由**

目的が分かれば、AIは指示にない細部も目的に沿って判断できます。範囲を決めないと、関係のないファイルまで変えることがあります。完了の条件がないと、どこまでやれば終わりかをAIが決めることになり、テストの追加や確認が抜けます。

**良い例**

```text
目的：注文一覧で、キャンセル済みの注文を表示しないようにしたい。
範囲：src/features/order-history/ の中だけを変更する。APIの型は変えない。
完了の条件：
- キャンセル済みの注文を除外することを確かめるテストを追加する
- npm test と npm run check が通る
```

**悪い例**

```text
注文一覧を直してください。
```

## 作業の終わりに確認と報告をさせる

`AGENTS.md` に、作業の終わりにテストとLintを実行させることと、報告させる内容を書きます。報告には、実行したコマンドと結果、規約から外れた箇所とその理由、対応しなかったことを含めます。

準拠レベル：**必須**

**理由**

実行結果が報告されていれば、レビューの前に、確認が済んでいるかが分かります。規約から外れた箇所を報告させるのは、[準拠レベル](/coding-guidelines/about/compliance/)の決まりに沿うためで、外れた理由が妥当かをレビューで判断できます。対応しなかったことを報告させないと、AIが黙って省いた作業に気づけません。

ただし、報告をそのまま信じてマージはしません。人が書いたコードと同じく、[レビュー](/coding-guidelines/workflow/review/)のページに沿ってレビューします。

**良い例**

```md title="AGENTS.md（一部）"
## 作業の終わりに

`npm test` と `npm run check` を実行し、すべて通ることを確認する。そのうえで、次を報告する。

- 変更内容の要約
- 実行したコマンドと結果
- 規約の必須・推奨のルールから外れた箇所と、その理由
- 依頼のうち対応しなかったことと、その理由
```

**悪い例**

```md title="AGENTS.md（一部）"
## 作業の終わりに

終わったら教えてください。
```

## AGENTS.mdの雛形

ここまでのルールをまとめた雛形です。〈 〉の部分をプロジェクトに合わせて書き換え、当てはまらない項目は削除して使います。

````md title="AGENTS.md"
# AGENTS.md

## このリポジトリについて

〈このリポジトリが何かを1〜2文で書く。例：注文管理画面のフロントエンド。React + TypeScript + Vite で作っている。〉

## コーディング規約

次の規約に従う。

https://ogitet.github.io/coding-guidelines/llms-full.txt

- 準拠レベルが必須と推奨のルールは、依頼で触れていなくても守る
- 必須または推奨のルールから外れた場合は、外れたルールと理由を報告する
- 準拠レベルが任意のルールは、既存のコードの書き方に合わせる

### このプロジェクトでの例外

規約の次のルールは、このプロジェクトでは適用しない。

- 〈ルール名〉：〈代わりにどうするか〉。〈理由〉

## コマンド

| コマンド | 内容 |
| :-- | :-- |
| `npm install` | 依存パッケージを入れる |
| `npm run dev` | 開発サーバーを起動する |
| `npm run build` | 本番用にビルドする |
| `npm test` | テストを実行する |
| `npm run check` | フォーマットとLintを確認する |

## 前提

〈コードを読んでも分からない前提だけを書く。例：`src/legacy/` は移行中の古いコード。2027年3月に削除するため、新しいコードから import しない。〉

## 作業の進め方

- 変更の前に、関係するファイルを読み、既存の書き方を確かめる
- 判断に迷う点は、作業を始める前に質問する
- 依頼された範囲の外は変更しない。範囲の外で見つけた問題は、報告にとどめる
- 新しい関数やコンポーネントを作る前に、同じ役割のものが既にないかを探す

## 事前に確認する操作

- 依存パッケージの追加、更新、削除
- フォーマッタ、Lint、TypeScriptの設定の変更
- 依頼された範囲の外にあるファイルの変更

## 禁止する操作

- テストの削除やスキップ、期待値を実装に合わせて書き換えることで、テストを通す
- 理由を書かずに、Lintの無効化コメント、`@ts-ignore`、`any` で警告やエラーを消す
- `git push --force` と、メインブランチへの直接のプッシュ
- `.env` で始まるファイルの読み書き

## 作業の終わりに

`npm test` と `npm run check` を実行し、すべて通ることを確認する。そのうえで、次を報告する。

- 変更内容の要約
- 実行したコマンドと結果
- 規約の必須・推奨のルールから外れた箇所と、その理由
- 依頼のうち対応しなかったことと、その理由
````

Claude Codeを使う場合は、あわせて次の `CLAUDE.md` を置きます。

```md title="CLAUDE.md"
@AGENTS.md
```
