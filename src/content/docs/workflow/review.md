プルリクエストのレビューの進め方と、レビューで確かめる観点を決めます。前半はレビューの進め方のルール、後半の「[チェック項目](#チェック項目)」は、レビューで確かめる観点の一覧です。

チェック項目は観点だけを並べ、ルールの中身は書きません。各ルールの内容と理由は、リンク先のページを参照してください。プルリクエストの作り方とマージの条件は[Git](/coding-guidelines/workflow/git/)で扱います。

## レビューを依頼する前に、自分で差分を見直す

レビューを依頼する前に、プルリクエストの画面で差分を最初から最後まで読み、このページのチェック項目に沿って自分でレビューします。1人で開発している場合も、マージする前に同じようにレビューします。

準拠レベル：**推奨**

**理由**

エディタで書いているときは、変更した箇所の周りしか見ていません。差分として通して読むと、消し忘れたデバッグ用のコード、関係のない変更、説明の足りない箇所などに気づけます。自分で見つけられる問題を先に直しておけば、レビューする人は、書いた本人には気づけない問題に集中できます。

**良い例**

```md
<!-- プルリクエストの説明 -->
## レビューしてほしい点

- 自分でレビュー済みです
- 送料の計算をフックに置くか関数に置くかで迷いました。calculate-shipping-fee.ts を特に見てください
```

**悪い例**

```diff
// 自分で見直さずに依頼し、デバッグ用のコードが残っている
+ console.log("ここまで来た", order);
+ const total = calculateTotal(order.items);
```

## CIが通ってからレビューを始め、ツールで検出できることは指摘しない

レビューは、CI（フォーマット、Lint、テスト）がすべて通ってから始めます。書式やLintで検出できることは、レビューで指摘しません。

準拠レベル：**推奨**

**理由**

CIが失敗している状態でレビューすると、CIを直したときに変わる部分まで読むことになり、時間が無駄になります。書式やLintで検出できることはツールに任せ、レビューでは、仕様に合っているか、設計が妥当かといった、人にしか判断できないことに時間を使います。

同じ指摘を繰り返している場合は、Lintのルールにできないかを検討します（[フォーマットとLint](/coding-guidelines/common/format-and-lint/)を参照）。

**良い例**

```md
<!-- レビューコメント -->
[質問] 注文が0件のときは、APIが空の配列を返す前提でよいですか？ null が返る場合の扱いがないように見えます。
```

**悪い例**

```md
<!-- レビューコメント -->
ここのインデントがずれています。
セミコロンが抜けています。
```

## 目的と設計から確かめ、細部はその後に見る

レビューでは、まずプルリクエストの説明を読み、変更が目的を満たしているかと、設計の方針が妥当かを確かめます。命名や書き方などの細部は、その後に見ます。

準拠レベル：**推奨**

**理由**

設計の方針に問題があると、細部を整えても、作り直すときにすべて無駄になります。先に大きな問題を伝えれば、書いた人は早い段階で手戻りできます。細部の指摘ばかりが並ぶと、本当に直すべき問題が埋もれます。

**良い例**

```md
<!-- レビューコメント（1回目） -->
[必須] 送料の計算がカートとお届け先の画面の両方に書かれています。
calculate-shipping-fee.ts のような関数に切り出して、両方から使う形にしませんか？
細かい点は、方針が決まってから見ます。
```

**悪い例**

```md
<!-- レビューコメント（1回目） -->
- 変数名 fee は shippingFee のほうが分かりやすいです
- この行は1行にまとめられます
- コメントの句点が抜けています
<!-- 3回目のレビューで、設計の作り直しを依頼する -->
```

## 誰が書いたコードも同じ基準でレビューする

書いた人が経験の長い人でも、AIでも、自分でも、同じ基準でレビューします。書いた人を理由に、レビューを省いたり基準を下げたりしません。

準拠レベル：**必須**

**理由**

マージした時点で、コードの品質の責任は、承認した人とマージした人が負います。「詳しい人が書いたから」「AIが書いたから」と読み流すと、その部分だけ品質が落ちます。特にAIのコードは、見た目が整っていてもっともらしく読めるため、注意して読まないと誤りを見落とします。

**良い例**

```md title="プルリクエストの説明（一部）"
## 確認したこと

- レビューのページのチェック項目をすべて確認した
```

**悪い例**

```md title="プルリクエストの説明（一部）"
AIが生成したコードのため、細かいレビューは省略しています。
```

## 説明できないコードは承認しない

差分のコードは、1行ずつ、何をしているかと、なぜそう書くのかを説明できるまで読みます。説明できない箇所は、書いた人に説明を求めて公式のドキュメントで裏を取るか、説明できる書き方に直してもらいます。自分で書いたコードも、説明できないままマージしません。

準拠レベル：**必須**

**理由**

説明できないコードは、不具合が起きたときに直せず、変更してよいかも判断できません。ほかから写したコードやAIが書いたコードは、説明できないまま取り込まれやすく、説明も誤っていることがあるため、聞くだけで済ませずドキュメントで確かめます。読んで分からないコードは、後で読む人にも分からないため、書き方を直す理由になります。

**良い例**

```ts
// 8〜64文字で、数字、英小文字、英大文字をそれぞれ1文字以上含む
const isValidPassword =
  password.length >= 8 &&
  password.length <= 64 &&
  /\d/.test(password) &&
  /[a-z]/.test(password) &&
  /[A-Z]/.test(password);
```

**悪い例**

```ts
// 先読みの意味と、使える記号の範囲を説明できないまま取り込んでいる
const isValidPassword = /^(?=.*\d)(?=.*[a-z])(?=.*[A-Z])[\w!@#$%^&*]{8,64}$/.test(password);
```

## 指摘には重要度のラベルを付ける

レビューのコメントの先頭には、次のラベルのいずれかを付けます。

| ラベル | 意味 | 対応 |
| :-- | :-- | :-- |
| `[必須]` | 不具合、セキュリティの問題、規約の必須のルールへの違反 | マージする前に直す |
| `[推奨]` | より良い書き方の提案、規約の推奨のルールへの違反 | 直すか、直さない理由を返信する |
| `[質問]` | 意図や前提の確認 | 返信する |
| `[軽微]` | 好みに近い小さな提案 | 直すかは書いた人が決める |

準拠レベル：**推奨**

**理由**

ラベルがないと、書いた人は、すべての指摘を直さなければならないのか、どれが重要なのかを判断できません。重要度が分かれば、`[必須]` から優先して対応でき、`[軽微]` の指摘をめぐって議論が長引くことも防げます。

`[必須]` と `[推奨]` は、[準拠レベル](/coding-guidelines/about/compliance/)の必須と推奨にそろえています。

**良い例**

```md
[必須] review.body を dangerouslySetInnerHTML で入れているため、XSSが起きます。JSXの式で入れてください。

[軽微] ここは早期リターンにすると、ネストが1段浅くなります。
```

**悪い例**

```md
dangerouslySetInnerHTML はやめてください。

ここは早期リターンにしてください。
```

## 指摘には理由を書き、規約にあるものはリンクする

指摘には、なぜ直したほうがよいのかを書きます。この規約のルールに基づく指摘は、そのルールへのリンクを付けます。

準拠レベル：**推奨**

**理由**

理由のない指摘は、書いた人が納得できず、同じ問題を別の箇所で繰り返します。理由が分かれば、書いた人が自分で判断できるようになります。規約へのリンクがあれば、レビューする人の好みではなく、決めたルールに基づく指摘であることが分かります。

**良い例**

```md
[必須] 閉じるボタンがアイコンだけで、名前がありません。
スクリーンリーダーでは「ボタン」としか読み上げられず、何のボタンか分かりません。
https://ogitet.github.io/coding-guidelines/quality/accessibility/#アイコンだけのボタンやリンクに名前を付ける
```

**悪い例**

```md
[必須] ここはよくないので直してください。
```

## 指摘はコードに対して行い、書いた人を評価しない

レビューのコメントでは、コードについて述べます。書いた人の能力や姿勢についての言葉は使いません。良い書き方を見つけたときは、それも伝えます。

準拠レベル：**必須**

**理由**

レビューの目的は、コードの品質を上げることです。人を責める言い方をされると、書いた人は指摘を受け入れにくくなり、次から相談せずに書くようになります。指摘をコードに向ければ、書いた人とレビューする人が、同じ問題を一緒に解く立場になります。

**良い例**

```md
[推奨] この関数は、注文が0件のときに undefined を返すようです。空の配列を返すと、呼び出し側で分岐が要らなくなります。

テストの名前で仕様が読めるので、とても分かりやすいです。
```

**悪い例**

```md
なぜこんな書き方をしたんですか？ 基本ができていないと思います。
```

## 画面の変更は、レビューする側も動かして確かめる

画面の表示や操作に関わる変更は、レビューする人も、プレビュー環境や手元で実際に動かして確かめます。差分を読むだけで承認しません。

準拠レベル：**推奨**

**理由**

レイアウトの崩れ、操作したときの違和感、読み込み中やエラーのときの表示などは、コードを読むだけでは分かりません。書いた人が確かめた環境とは別の環境で動かすことで、書いた人が見落とした問題も見つかります。

**良い例**

```md
<!-- レビューコメント -->
iPhone（Safari）で確認しました。絞り込みのダイアログを開いたとき、背景がスクロールしてしまいます。
```

**悪い例**

```md
<!-- レビューコメント -->
コードを読んだ限り問題なさそうなので承認します。
```

## `[必須]` の指摘がすべて解消してから承認する

承認は、`[必須]` の指摘がすべて直り、`[推奨]` と `[質問]` の指摘に返信があってから行います。「直しておいてください」と書いて、直る前に承認しません。

準拠レベル：**必須**

**理由**

承認すればマージできる状態になるため、直る前に承認すると、直さないままマージされることがあります。直したことを確かめてから承認すれば、指摘が確実に反映されます。

**良い例**

```md
<!-- レビューコメント（2回目） -->
XSSの修正を確認しました。承認します。
```

**悪い例**

```md
<!-- レビューコメント（1回目） -->
[必須] XSSが起きるので直してください。承認しておきます。
```

## チェック項目

レビューで確かめる観点の一覧です。自分でレビューするときも、ほかの人のコードをレビューするときも使います。変更に関係しない項目は飛ばします。

### 目的と仕様

- [ ] プルリクエストの説明に、目的、変更内容、確認したことが書かれているか（[Git](/coding-guidelines/workflow/git/)）
- [ ] 変更が目的を満たしているか。目的と関係のない変更が混ざっていないか
- [ ] 何をしているかを説明できない箇所が残っていないか（[説明できないコードは承認しない](#説明できないコードは承認しない)）
- [ ] データが0件、文字列が長い、読み込み中、エラーといった状態を扱っているか（[検証](/coding-guidelines/quality/verification/)）

### 設計と構成

- [ ] 同じ処理を重複して書いていないか

### 命名とコメント

- [ ] 名前の記法と、語の選び方が決まりに沿っているか（[命名規則](/coding-guidelines/common/naming/)）
- [ ] コメントに「なぜ」が書かれているか。コードとコメントが食い違っていないか（[コメント](/coding-guidelines/common/comments/)）
- [ ] Lintのルールを無効にしている箇所に、範囲の指定と理由があるか（[フォーマットとLint](/coding-guidelines/common/format-and-lint/)）

### 技術別

- [ ] HTMLの要素と属性の使い方、ページのメタデータが決まりに沿っているか（[HTML](/coding-guidelines/tech/html/)）
- [ ] CSSの書き方とクラス名の付け方が決まりに沿っているか（[CSS](/coding-guidelines/tech/css/)）
- [ ] 型の書き方が決まりに沿っているか（[TypeScript](/coding-guidelines/tech/typescript/)）
- [ ] コンポーネントの設計、Hooks、状態管理が決まりに沿っているか（[React](/coding-guidelines/tech/react/)）

### アクセシビリティ、画像、パフォーマンス

- [ ] 要素の意味、代替テキスト、ラベルと `autocomplete`、キーボード操作、コントラスト比が決まりに沿っているか（[アクセシビリティ](/coding-guidelines/quality/accessibility/)）
- [ ] axeで違反がなく、キーボードだけで操作できることを確かめたか（[検証](/coding-guidelines/quality/verification/)）
- [ ] 画像の形式、サイズ、`width` と `height`、読み込みの方法が決まりに沿っているか（[画像](/coding-guidelines/common/images/)）
- [ ] フォント、依存パッケージ、外部のスクリプト、後から表示する要素の扱いが決まりに沿っているか（[パフォーマンス](/coding-guidelines/quality/performance/)）

### テストと検証

- [ ] 追加・変更したロジックにテストがあるか。不具合の修正に、再現するテストがあるか（[テスト](/coding-guidelines/quality/testing/)）
- [ ] テストが実装の詳細ではなく、振る舞いを確かめているか（[テスト](/coding-guidelines/quality/testing/)）
- [ ] 対応するブラウザとデバイスで表示と操作を確かめたか（[検証](/coding-guidelines/quality/verification/)）

### Git

- [ ] コミットメッセージが決まった形式で、1つのコミットに1つの変更だけが入っているか（[Git](/coding-guidelines/workflow/git/)）
- [ ] 作業途中のコミットが、マージの前に整えられているか（[Git](/coding-guidelines/workflow/git/)）
